作成日：2026年10月28日

検索の実測とページ別の優先順位は、[2026年10月28日の検索実測・移行戦略](検索実測と移行戦略_2026-10-28.md)を参照する。Google実画面で15語を確認した記録であり、Search Consoleの実流入は未取得。

## 1. 目的と基本方針

現在の検索向け設定とページの情報を引き継ぎ、デザイン変更に伴う検索流入への影響をできるだけ抑える。検索順位や検索結果の表示内容の完全な維持は保証できない。

原則として、ドメイン・各ページのURL・主要本文を維持してデザインを変更する。ページ統合、URL変更、大幅な本文削除は別の変更として管理する。古い募集情報や誤記は残さず、変更内容を記録する。

移植対象はHTMLに出力される情報とURLであり、現在のReactやNext.jsのコードをそのまま使う必要はない。デザインの色・配置・フォントは変更できる。

Google公式：[URL変更を伴う移行](https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes)、[URLを変えないホスティング移行](https://developers.google.com/search/docs/crawling-indexing/site-move-no-url-changes)

## 2. 現在の工夫と引継ぎ方法

| 対象 | 現行の場所・内容 | 新サイトで行うこと |
|---|---|---|
| ドメイン・HTTPS | `https://keisuiryo.jp/` | 同じドメインを継続。HTTPSと証明書を確認する |
| ページURL | `next.config.js` の `exportPathMap`、末尾スラッシュあり | 下記のURL台帳を維持し、直接アクセスでも表示する |

| 静的HTML | `next.config.js` の `output: 'export'` | 主要本文・タイトル・説明文・リンクが初期HTMLに含まれる静的生成／サーバー生成を推奨する |

| Search Console | リポジトリだけでは設定不明 | 現管理者から所有権・アクセス権・確認方法を引き継ぐ。認証タグ／ファイル／DNSレコードを使っている場合は維持する |

`description` は検索結果の説明文の候補であり、表示内容はGoogleが判断する。構造化データも特別な検索表示を保証しない。

各URLについて次の記録を作り、公開後に埋める。

| 旧URL | 新URL | 対応（維持／転送／廃止） | タイトル・説明文 | 主要本文 | 公開後HTTP状態 | 確認者・日付 |
|---|---|---|---|---|---|---|
| 例：`https://keisuiryo.jp/meals/` | 同左 | 維持 | 引継ぎ確認 | 引継ぎ確認 | 200 | 未確認 |

URLを変える場合は関連する新ページへHTTP 301または308で直接転送し、少なくとも1年間維持する。全旧ページをトップへ一括転送しない。対応先がなく完全に廃止するページは404または410を返す。意図した廃止による検索掲載の消失は、デザイン移行の不具合と区別する。

GitHub Pagesを継続する場合、HTMLの自動転送をHTTP 301と同一視しない。必要な転送を実現できる配信基盤を事前に確認する。URLが同じなら移行用転送は不要。ドメイン変更を伴わないデザイン変更でSearch Consoleの「アドレス変更」は使わない。

Google公式：[URL対応表と転送](https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes)

## 4. 現行の不備を修正して移す

### 4.1 構造化データ

現行の `meta.js` はJSON-LDを文字列で組み立てており、配列・オブジェクトの末尾カンマが含まれる。2026年10月28日には本番トップとFAQから取り出したJSON-LDをパーサーに渡し、両方で構文エラーを確認した。そのままコピーしない。

新実装ではオブジェクトからJSONを生成し、実際に出力された全ページのJSON-LDをJSONパーサーで確認する。テンプレート内の値や引用符、HTMLへの安全な埋め込みも確認する。

現行トップは `Apartment`、下層は `WebSite` と `BreadcrumbList` を使用している。型を機械的に維持せず、ページや施設の実態に合うかを確認する。住所・電話・緯度経度・SNS・営業時間・創設者なども、本文と一致する正確な値だけを残す。下層ページの情報をサイト全体と混同しない。

現在のURL生成は `"https://keisuiryo.jp/" + props.id`。本番トップの `og:url` が `https://keisuiryo.jp/undefined` であることを確認した。下層の末尾スラッシュも公開HTMLで確認し、ページごとの正しい絶対URLを生成する。画像も実在する公開URLを指定する。

[Rich Results Test](https://search.google.com/test/rich-results) と [Schema Markup Validator](https://validator.schema.org/) を併用する。Googleのテストが対応しない型は、リッチリザルトが検出されないことだけで構文不正と判断しない。

### 4.2 サイトマップと画像

現行サイトマップには `/facility/`（現行ページは `/facilities/`）、`/assets/` を含む旧画像・資料パス、理事写真への参照がある。存在や対応先を確認して訂正する。未確認の旧URLに推測で転送を設定しない。

新サイトマップには公開する正規URLを掲載し、404、転送先ではない旧URL、検索対象外ページを混ぜない。画像拡張を残す場合は画像の取得も確認する。`priority` の数値を上げてもGoogleの順位指定にはならず、Googleはこの値を無視する。

サイトマップから理事写真を外すだけでは画像の削除・検索除外にならない。写真ファイルそのものを非公開にする必要があるかは、本文削除とは別に判断する。

Google公式：[サイトマップの作成](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap)

### 4.3 正規URLと内容の整合

現行の共通メタ実装には `canonical` がない。新サイトでは、各公開ページの正規URLを絶対URLで設定する。全ページのcanonicalをトップへ向けない。内部リンク・サイトマップ・canonicalでURLを一致させ、開発用ドメインを残さない。canonicalは転送の代替ではない。

トップの説明文には「2026年度」、本文には「2027年度」と閉寮年度の不一致がある。正しい事実を確認して統一する。募集の現状、寮費の不一致なども確認し、検索対策のために古い事実を温存しない。

Google公式：[正規URLの指定](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls)

## 6. 新デザインを作るときの要件

1. 最初に既存URLごとのページを用意し、本文・見出し・著者・メタ情報を移す。その後にレイアウトを調整する。
2. 主要本文は初期HTMLへ出力し、画像内の文字や操作後にしか取得できない内容へ置き換えない。JavaScriptを使う場合も、Googleが描画した結果を確認する。
3. メニューはキーボード・スマートフォンでも操作でき、リンクに実際の `href` を持たせる。重要ページが孤立しないようにする。
4. 大きな画像を適切に圧縮し、幅・高さを指定する。装飾画像や動画の追加で表示速度やレイアウトの安定性が大きく悪化しないか比較する。
5. 検証サイトは認証で保護するなどして重複公開を防ぐ。`noindex` を使う場合、Googleがその指定を読めることが必要であり、robots.txtで遮断するだけでは検索除外を保証しない。
6. 新旧サイトの公開URLで同じページのHTTP状態・主要本文・タイトルを比較する。デザインが表示されるだけで完了としない。
7. 折りたたみの回答や献立は初期HTMLにも含める。クリックして初めてAPIから取得する方式へ変更する場合は、同等に取得できることを別途検証する。
8. トップにある食事・費用・定員・通学の説明を維持する。食事の専用ページだけに集約したり、お知らせだけのトップへ変更したりしない。

Google公式：[JavaScript SEO](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics)

- [ ] Search Consoleの所有権確認が継続する。GA4が二重送信なく計測できる。
- [ ] 元に戻す成果物と手順が用意されている。

HTTP確認例（本番または実際の配信先で実行）：

```sh
curl -sS -o /dev/null -w '%{http_code}\n' https://keisuiryo.jp/about/
curl -sS -D - -o /dev/null https://keisuiryo.jp/about/
curl -sS -o /dev/null -w '%{http_code}\n' https://keisuiryo.jp/seo-check-page-that-does-not-exist/
```

最初は維持ページの状態、次は応答ヘッダー、最後は存在しないURLの404を確認する例。これだけで本文・描画・構造化データの検証を代替しない。

## 8. 公開・公開後の確認

### 公開当日

1. 合格条件を満たした成果物を公開し、公開コミット・日時を記録する。ホスティング変更時はDNS・証明書・カスタムドメインを確認する。
2. 本番URLで第7節を再確認する。Gitへのpush、デプロイ成功、本番での正常表示はそれぞれ別に記録する。
3. Search ConsoleのURL検査でトップ・主要な流入ページ・変更したページを確認する。ライブテストと、Googleの既存インデックス情報は区別する。
4. 更新したサイトマップをSearch Consoleへ送信する。所有権確認や送信が未実施なら、その状態を記録する。
5. GA4で実際のアクセスを確認する。

### 公開後の運用目安

最初の1週間は日ごと、その後は週ごとに少なくとも1か月確認する。これは本マニュアルの運用目安であり、Googleが再評価を完了する期限ではない。Search Consoleには集計の遅延もある。

| 確認対象 | 問題があった場合 |
|---|---|
| 検索クリック・表示回数・掲載順位 | ページ別・検索語別に移行前と比較。季節性、曜日、募集内容の変更も考慮する |
| ページのインデックス状況 | noindex、取得エラー、canonical、本文欠落、転送を調べる |
| 404と転送 | 台帳にある維持ページや外部リンク先が壊れていないか調べる |
| 構造化データとサイトマップ | 新しいエラーや取得失敗を調べる |
| アクセス計測 | 実際の流入減少とタグの計測漏れを区別する |

サイト全体のnoindex、重要ページの大量404、本文欠落、継続する5xx、転送ループがあれば、直ちに修正する。短時間で修正できなければ保存した正常な成果物・配信設定へ切り戻し、本番を再確認する。検索順位の一時変動だけで何度もデザインを切り替えない。
